# ADR 0020: Profile-linked application tracking

**Status:** Accepted  
**Date:** 24 August 2026

## Context

Government application references are system identifiers, not information citizens should be expected to memorize. Asking for one as the default tracking entry point creates avoidable recall work and is especially unfriendly on a mobile device. Sarathi already has a signed-in citizen profile and starts guided service journeys, so it can retain the acknowledgement generated by those journeys.

## Decision

Applications started or saved through Sarathi appear as recent applications in the citizen profile. Tracking starts from the selected application and uses its stored acknowledgement automatically. The reference remains visible as supporting detail, not as the primary interaction. Manual reference entry is retained only for applications started outside Sarathi or not found in the profile.

The hackathon build uses synthetic in-memory data. A production implementation must retrieve profile-linked applications through approved integrations, encrypt identifiers, apply retention and deletion policy, and allow citizens to remove saved applications.

## Rationale

- Removes unnecessary recall and transcription errors.
- Makes repeat status checks one tap.
- Preserves an escape hatch for externally initiated applications.
- Keeps the official identifier visible for transparency and support.

## Consequences

- The profile becomes the application-history root.
- Product copy must distinguish saved applications from live government status.
- Production needs secure account linking, consent, synchronization, and stale-state handling.

## Alternatives considered

- Keep a pre-filled reference input: rejected because it still frames memorization as the normal task.
- Hide references entirely: rejected because citizens may need them for official support and portal handoff.

## Review trigger

Review when approved status APIs, account-linking requirements, or retention rules are known.
